# ADR-0004: Trust manifest and single-use approval receipt

**Status:** Accepted; approval portion superseded by ADR-0005  
**Date:** 2026-08-14

> Historical note: this ADR documents Engine 0.2.0 and Approval Receipt v2. ADR-0005 replaces the approval protocol with signed Consent Request and locally signed Receipt v3; the trust-manifest decision remains active.

## Context

A playbook signature proves authorship only when its public key is obtained through a trusted and revocable channel. An approval receipt also needs replay protection, a short lifetime, installation binding, and a strict separation from AI recommendations.

## Decision

Nara uses a two-level signing hierarchy:

1. An offline root key signs a versioned trust manifest.
2. The trust manifest publishes playbook release keys and marks each key `active`, `retired`, or `revoked`.
3. An active release key signs the exact playbook bytes.

The engine embeds only the root public key. It verifies the trust-manifest signature and validity window before resolving the playbook key. New execution accepts only an active, unexpired, non-revoked release key. Rotation is tested by retiring the old key and activating a new key. Revocation is tested with a separately root-signed manifest.

Approval Receipt v2 is simulation-only and contains:

- a unique approval ID and session nonce;
- a random local installation ID, not a hardware serial;
- hashes of the exact action plan and playbook;
- the verified playbook signing-key ID;
- the exact approved action IDs;
- `recommended` approval mode;
- a maximum ten-minute validity window;
- a single-use flag.

The engine records the approval ID in every ledger event and rejects a replay already observed in the installation ledger. Engine 0.2.0 additionally restricts execution to low-risk actions that do not require Administrator.

## Security boundary

The current root and release hierarchy is a development simulation. Its private keys were discarded after signing fixtures and are not stored in the repository. It is not a production key ceremony.

The receipt is currently generated by the test harness and is therefore not proof of a real user click. Production requires a fixed, protected ledger location plus an Approval Broker whose local signing key is protected by Windows CNG/DPAPI and whose UI displays the exact action details before issuing a receipt. AI cannot call that signing boundary directly.

## Consequences

- Modifying a manifest, playbook, plan, signing-key ID, installation ID, or approved action set causes rejection.
- A revoked or retired release key cannot authorize new execution.
- Reusing a consumed receipt in the same installation ledger is rejected.
- Production key generation, storage, rotation ceremony, revocation publication, and Approval Broker UI remain explicit release gates.
